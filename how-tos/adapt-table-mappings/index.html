Adapt table mappings to your application's data

Use these recipes when your application needs a different input shape, matching rule, or output grid. Each starts from named prepared tables and shows the JSON record to add or replace in table_mapping.json.

Core supports typed row and concat constructors, bindings for whole values, and the final columns projection used in these recipes. The reference for table mappings defines their fields, order, types, and null behavior.

Declare dependencies before their consumers. The JSON objects below are table records to place inside the top level list, not separate configuration formats. For exact field definitions, see the reference for table mappings. If you are learning the format, start with the reserve requirement tutorial.

Point each dependent table at supported_technologies. The filtered projection is evaluated once at that boundary and kept in memory for those downstream plans. Materialization moves lazy errors in the final projected plan to assembly time and holds the complete result in memory. Keep the default lazy behavior for large tables or tables used only once.

For a build that covers several years, remove the filter by year and keep solve_year in the output. Do not bind a list to this equality comparison and expect it to match any item in the list. Join on every dimension that determines the price. Do not match on category alone when the same category has different prices across regions or years.

For 2032, the two costs are 300 and 400. For 2040, they are 400 and 200. Omitting solve_year from on would match each quantity to prices from both years.

If prices are global, remove region from the price source and the join keys. Keep it in the quantity table and grouping keys when regional totals are still required. If prices are hourly, carry datetime on both sides and add it to the join keys.

This inner join retains priced rows only. Account for every required price key before accepting totals. To inspect missing prices, use a left join and inspect null price_per_mwh values before aggregation. A left join alone does not make the total complete, because sum ignores null contributions. Do not fill an unknown price with zero unless that is an explicit application policy.

To preserve unknown samples, omit fill_null and let the consumer’s null policy apply. To use a different time range or resolution, change the prepared calendar and the parser’s time axis settings together. Do not infer a calendar from sparse observations.

Keep grid keys unique when one row per key is required. Cross joins preserve duplicate owners, years, and timestamps. They do not deduplicate them for you.

Diagnose an unexpected result

Section titled “Diagnose an unexpected result”

Inspect the named intermediate table immediately before the unexpected change.

SymptomCheck
A category disappearsExact category and factor labels, plus every inner join key.
Totals are unexpectedly multipliedDuplicate matches on the right or a missing year, region, or product key.
A new source cannot concatenateMatching output names and compatible column types in its final projection.
Product metadata becomes measurement rowsExplicit unpivot.columns and index, not an assumption about every remaining column.
Missing requested periodsThe grid inputs, rather than just the observation timestamps.
Unknown prices appear as zero costsMissing price matches, nulls before aggregation, and any fill_null policy.
Values are correct but attachment failsOwner names, metadata partitions, and the parser’s time axis requirements.

For null, availability, and duplicate behavior, use the table mapping reference.
